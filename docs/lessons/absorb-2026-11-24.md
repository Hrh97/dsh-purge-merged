### 巡检脚本连带修的三个 bug（2026-11-24，网络 brownout 逼出来的）

补完 4 个仓后重跑，58 行**全 partial**。逐层挖下去发现三个独立 bug 叠在一起：

**Bug 1：一次失败就熔断整轮（最致命）**
旧 `lsRemote()` 只有 https 一条通道，且第一次撞网络错就 `NET_DOWN = true`。这个标志会让
`api()` 也一起熔断 —— 于是一台机器的网络抖动被放大成「后面所有仓全部 partial、基线全废」。
现场表现极有迷惑性：**前 24 个 ok、后 32 个 partial**，看着像「仓库列表后面的有问题」，
其实是「第 25 个仓刚好赶上网络抖动，后面全被连坐」。
修法：拆成三层 ——
- `GIT_TRANSPORT`（https / ssh）：只管 git 取 HEAD 的通道，**粘性**，某条通了就一直走它；
- `CONSEC_FAIL`：连续失败计数，连续 5 个仓两条通道都失败才置 `NET_DOWN`；
- 单个仓失败不再连坐后续仓。

**Bug 2：`GIT_TERMINAL_PROMPT` 没设 0 → 公共仓被判 gone**
git 在拿不到凭据时会弹交互式用户名提示，在无控制台的子进程里变成
`error: failed to execute prompt script (exit code 1)`。老代码把这类错误归到「仓库不可访问」，
于是 **`Goochbeater/Spiritual-Spell-Red-Teaming` 这类正常公共仓被误判成 404**。
修法：`execFile` 的 `env` 里加 `GIT_TERMINAL_PROMPT: "0"`。设 0 之后：
- 公共仓正常返回 HEAD；
- 私有/已删仓给出干净的 `could not read Username ... terminal prompts disabled`，可据此判 gone。

**Bug 3：SSH 认证失败被误判成 404**
`ERROR: Repository not found` 在 SSH 认证失败时也会出现 —— 那说明**通道坏了**，不是仓没了。
修法：缺失判定用 `MISSING_RE`，并用 `AUTH_RE`（Authentication failed / Permission denied /
could not read Username）做排除；只有「通道本身可用 + 报缺失」才认 gone。

**附带**：`https` 与 `ssh` 会**交替 brownout**（几秒挂、几秒好），所以两条通道都撞网络错时
对该仓做一次 2.5s 后的重试 —— brownout 常常秒好。
